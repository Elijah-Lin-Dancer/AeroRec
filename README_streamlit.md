# AeroRec · 出行智能推荐中台

> 面向出行消费场景（机票 / 酒店 / 商城 / 营销 / 直播）的开源智能推荐中台 Demo。
> 工程化复现工业级推荐链路：**召回 → DeepFM CTR 排序 → 5 步混排 → 降级兜底 → 真实 CTR 评估**。

本应用是 [AeroRec](https://github.com/Elijah-Lin-Dancer/AeroRec) 的**在线交互体验入口**。

## 关于本实例的口径（请先读）

本实例运行的是**极轻档（micro）**：**1 万用户 × 1 万物品 × 50 万曝光**
（仓库完整档为 10 万 × 10 万 × 500 万）。

因此：

- **数据全部为合成生成**（`src/data/synthetic_generator.py`，固定随机种子），
  **不使用、也不声称使用任何真实业务数据**。选用合成数据是因为它让「潜在真实 CTR」
  成为已知量，从而能构造 **Oracle 上界**、给出**不依赖平滑估计**的评估口径——
  这是本项目量化结论得以成立的前提。代价见文末「诚实边界」。
- 本实例**仅用于交互体验**（点选用户、查看推荐、观察混排过程、跑通评估口径）。
- **规模差异**：数据越稀疏，相对增益越低，**不作为论文口径**。
- 论文级可引用结论一律以**完整档离线复现**为准（见仓库 README 与展示页）。

## 一个值得说明的工程取舍：为什么是 micro 档 + 离线预训练

在线免费托管的资源**是一个区间、不是固定值**。Streamlit Community Cloud 官方限额
（2024-02 起未变）：

| 资源 | 官方限额 |
|---|---|
| CPU | **0.078 核**（下限）～ **2 核**（上限） |
| 内存 | **690 MB**（下限）～ **2.7 GB**（上限） |
| 存储 | 无下限 ～ 50 GB |
| GPU | 无 |
| 休眠 | 无流量 **12 小时**后休眠 |

所有应用共享同一池资源，压力大时会被压缩到接近下限。因此本项目的设计基准
取**下限 690MB**（最坏情况），而不是「1GB」这类常见说法。

在这个约束下，量了两种运行方式的**框架基线**（同进程加载，未含数据）：

| 进程内同时加载 | 框架基线 RSS | 690MB 下留给数据的空间 |
|---|---|---|
| torch + sklearn + numpy + streamlit（**解耦前**） | **673 MB** | **16.7 MB** → 必然 OOM |
| numpy + streamlit（**解耦后**） | **73 MB** | 617 MB |

也就是说，**只要 `import torch` 就固定吃掉约 500–650MB（随 wheel 与版本浮动），
与数据规模无关**。673MB 的框架基线在 690MB 下限上只剩 16.7MB——
**连数据都装不下，再压数据也没用**。

因此本项目把**训练与推理解耦**：

1. **离线（本机）** 用 torch 训练 DeepFM(CTR) 与 LR(CVR)；
2. 把权重**导出为 numpy 数组**（`python -m src.build_online_artifacts micro`）；
3. **在线侧只加载权重**，用纯 numpy 复现前向计算，不依赖 torch/sklearn。

**端到端实测**（真实 streamlit 进程 + 浏览器驱动）：

| 阶段 | 进程 RSS |
|---|---|
| ① 仅启动 streamlit，无人访问 | 79.4 MB |
| ② 页面加载完（引擎与数据就位） | 187.0 MB |
| ③ 跑完最重操作（真实 CTR 对比，200 用户 / Top-20） | **297.2 MB** ← 真实峰值 |

| | 解耦前（在线训练） | 解耦后（加载 numpy 权重） |
|---|---|---|
| 框架基线 | 673 MB | **73 MB** |
| 实测峰值 | 超出 690MB 下限 | **297 MB** |
| 相对 690MB 下限的余量 | 0.98×（**必然 OOM**） | **2.3×** |
| 启动耗时 | 数十秒（需在线训练） | **约 1 s** |

**数学等价性已逐样本校验**：PyTorch 与 numpy 前向的最大偏差为 **1.19e-07**。
即：本实例演示的**仍是同一个已训练模型**，只是换了一种运行时执行。

**算力侧也有余量**：最重操作是「模拟 A/B」（2000 用户），本机实测 **1.87s**；
即便按最坏的 0.078 核折算（约 12.8× 减速）也在 **24s** 量级，不触发超时。

> 这类「先量清楚约束在哪、再决定动哪一层」的判断，本身就是本项目想展示的工程能力。

## 四个页面

| 页面 | 内容 | 口径 |
|---|---|---|
| 推荐演示 | 选用户 → 出 Top-K 推荐，每项带预估 CTR / CVR 与基础分 | — |
| 排序流程 | 展示 5 步混排的中间态：归一化 → 多目标加权 → 分层 → 同品类打散 → 去重 | — |
| **真实 CTR 对比** | 用已知的**潜在真实 CTR** 计算各方法 Top-K 平均点击率，并给出逐用户候选池 **Oracle 上界** | ✅ **可引用** |
| 模拟 A/B | 对照（热门）vs 实验（DeepFM+混排）的模拟在线 A/B，含显著性检验 | ⚠️ 仅供参考 |

### 两条评估口径的区别（重要）

**① 真实 CTR 对比（本 Demo 中最可信的一组数字）**

直接用已知的潜在真实 CTR 计算各方法 Top-K 列表的平均点击率，不依赖任何"平滑历史 CTR"估计，
因此**不受稀疏性偏差影响**。Oracle 上界 = 逐用户候选池（热门 ∪ 规则 ∪ 随机）内按真实 CTR 取 Top-K，
保证**严格 ≥ 所有被比较的方法**。

完整档实测（100 用户 / Top-10）：

| 方法 | 平均真实 CTR | 相对热门 | 占 Oracle 上界 |
|---|---|---|---|
| 随机 | 0.1652 | -66.4% | 23.1% |
| 热门 | 0.4922 | — | 68.8% |
| **DeepFM + 多目标混排** | **0.6323** | **+28.5%** | **88.4%** |
| Oracle 上界 | 0.7153 | +45.3% | 100% |

注：上表为**完整档（10 万物品 / 500 万日志）**的离线结果，也是唯一可引用的口径。
在线 micro 档为控制内存做了等比例缩小（**1 万用户 × 1 万物品 × 50 万曝光**），
真实 CTR 受候选池密度影响，增益会低于完整档——这是规模差异，不是实现差异。

**② 模拟 A/B（⚠️ 仅供形式对照，数字勿引用）**

热门基线按「历史日志的**平滑 CTR**」排序，而本项目日志是**随机曝光**生成的：
曝光次数少的物品一旦偶然被点击，平滑 CTR 就会被显著高估（贝叶斯平滑 α=5 不足以抵消）。
这属于推荐系统中的**位置偏差 / 数据稀疏偏差**。

- 完整档实测：热门榜 top200 平滑 CTR = 0.6231，真实 CTR 仅 0.2528，**偏差 +0.37**；
  平滑榜 top10 与真实 CTR top10 仅 **2/10** 重合。
- 后果：用「热门基线」作对照会**高估**推荐系统的相对收益。

> 本项目把这条偏差显式做成了页面提示，并把可引用口径单独拆成「真实 CTR 对比」页——
> 这本身就是本项目想展示的工程判断力：**先知道自己的指标哪里不可信，再谈提升。**

## 技术栈

- **召回**：热门兜底 / 规则召回（里程兑换、零库存、常驻地、多程返程）
- **排序**：DeepFM（FM 一阶 + 二阶交叉 + DNN，PyTorch 训练 / numpy 推理）做 CTR；LR 做 CVR，多目标加权
- **混排**：归一化 → 加权 → 分层排序 → 同品类打散 → 去重截断（默认 `w_base=0`，避免二次注入热门偏差）
- **降级**：CTR 预估异常 → 回退物品历史平均 CTR
- **评估**：离线 AUC 对比 + **真实 CTR 口径 + Oracle 上界** + 模拟在线 A/B（两比例 z 检验）

## 诚实边界

- 数据为本项目**合成**（受控实验），不使用、也不声称使用任何真实业务数据。
- **合成分布 → 真实分布的迁移性未验证**：本页所有指标衡量的是**方法在受控条件下的有效性**，
  不代表线上可迁移性。真实流的噪声、长尾与概念漂移均未覆盖。
- 生成公式中注入了隐式非线性交叉项（价格敏感×低价、商务×早班机、里程契合），
  模型只能拿到原始特征，交叉需自行学习——此为受控实验设置。
- 模型均使用**已有方法的实现**（DeepFM 为标准 DeepFM，Guo et al. 2017），本项目**不提出新算法**。
- 在线实例为极轻档，**这里的一切数值都只是体验演示**，不作为结论。
- 实习经历仅作为项目动机来源，实习中未涉及深度排序模型的训练。
- 评估口径的局限性已在代码与页面中显式标注（见 `src/eval/ab.py` 模块文档）。

## 本地运行

```bash
pip install -r requirements.txt   # 部署依赖（仅 numpy + streamlit，与 Cloud 一致）
streamlit run app.py                     # 默认 micro 档（1万×1万×50万，峰值约 297MB）
AEROREC_MODE=lite  streamlit run app.py  # 轻量档（2万×2万×100万，约 960MB）
AEROREC_MODE=full  streamlit run app.py  # 完整档（10万×10万×500万，需大内存）
```

> 若要复现**完整档**或离线重训模型（`full` 模式、`src.build_online_artifacts`），
> 需先安装完整依赖：`pip install -r requirements_full.txt`（含 torch / sklearn / pandas）。
> 根目录的 `requirements.txt` 之所以只有 numpy + streamlit，是因为 Streamlit Cloud
> 只读这个文件——若写入 torch，**框架基线会达 673MB，超过免费实例 690MB 的内存下限**，必然 OOM。

若 `artifacts/micro/` 缺失，先离线生成模型权重（需 torch，约 2 分钟）：

```bash
python -m src.build_online_artifacts micro
```

## 目录结构（与本应用相关部分）

```
app.py                        # Streamlit 入口
requirements.txt              # 部署依赖（仅 numpy + streamlit；Cloud 读取本文件）
requirements_full.txt         # 完整依赖（含 torch / sklearn，本地训练与离线复现用）
artifacts/micro/              # 离线预训练权重（numpy 格式）
  deepfm_ctr.npz              #   DeepFM 权重
  cvr_lr.npz                  #   LR(CVR) 系数
  meta.json                   #   规模/种子/维度元信息
src/
  config_scale.py             # 档位解析（micro / lite）
  config_micro.py             # 极轻档配置
  build_online_artifacts.py   # 离线训练 + 导出权重（需 torch）
  data/generator_common.py    # pandas-free 的生成基础量与真实 CTR 公式
  data/synthetic_generator_lite.py
  feature/lite_store.py       # numpy 特征库
  rank/numpy_deepfm.py        # DeepFM 的纯 numpy 前向（与 PyTorch 数值等价）
  rank/numpy_lr.py            # LR + OneHot 的纯 numpy 实现
  rank/mixer.py               # 5 步混排
  eval/ab.py                  # 真实 CTR 对比 + Oracle + 模拟 A/B（含偏差说明）
  serve/engine_micro.py       # 极轻档引擎（无 torch/sklearn）
```

注：数据由脚本**运行时合成**，不入库；首次打开需约 1 秒完成数据生成与权重加载。
